## Architecture review 2026-10-13

A review of the whole application: every non-test import was traced
(447 source files), the largest modules were read, and the documented
boundaries were compared with the code.

**Result.** The separation into renderer, main process, shared and
plugins is sound and is actually kept: no production file crosses a
boundary the wrong way, no plugin imports another, and the base imports
no plugin. The findings below are about what protects that state, and
about a few places where the base still knows more about a feature than
its own rules say it should. Ordered by value for effort.

**Status.** Findings 1, 2, 3, 6 and 7 were carried out on 2026-10-13
(roadmap items A1–A5; `specs/changelog.md`). The rows stay as the record
of what was found. Finding 7's possible defect was checked: the fixed
`templates/daily.md` is what the specs describe, so it stayed. All three
roadmap follow-ups shipped on 2026-10-17: the plugin specs are
typechecked in CI (`tsconfig.plugins.json`), `npm run cycles` fails on
runtime import cycles, and the composition root has unit tests
(`app-services.spec.ts`, `main-window.spec.ts` and the vault context in
`plugin-context.spec.ts`). Finding 4 was carried out on 2026-10-18
(roadmap item A6; the ADR-0010 later change "plugin settings live in the
plugin's own config"). Open: 5, 8 and 9.

| # | Finding | Evidence | Suggested step |
|---|---|---|---|
| 1 | **Most dependency rules are kept by habit, not by a check.** | Lint enforces the module barrels and the plugin rules for CodeMirror, Angular and Node. Nothing checks: `shared/` importing outward, renderer ↔ main, base → plugin, plugin → plugin, a plugin's main half → `electron/`. All five hold today. | Add them as `no-restricted-imports` patterns in `eslint.config.mjs`. Small, and it turns the table in [§5](05_building_block_view.md#the-dependency-rules) into something the build defends. Needs finding 2 first, because tests currently cross these lines. |
| 2 | **Tests live away from the code they test.** | `src/app/services/` holds 75 spec files; 13 test a file in that folder. The other 62 test `shared/`, `electron/` and plugin code — 26 of them import from `plugins/`, and the names `app-config.spec.ts` and `note-manager.spec.ts` exist both there and under `electron/`. They run in the Angular test runner although the code is plain Node or pure functions. | Move each spec next to its source and into the plain-Node suite (`vitest.plugins.config.mts`, which already covers `electron/` and `plugins/`; `shared/` would be added). A plugin's tests then travel with the plugin, and the two duplicated files can be merged. |
| 3 | **Two import cycles in the renderer.** | (a) Seven files: `vault/index.ts` exports both `VaultService` and `DailyNoteService`; `DailyNoteService` imports `EditorService`, which imports `VaultService` through that same barrel. (b) Six files: `plugin-host/` → `settings/settings-registry.service.ts` → back to `plugin-host/` (`PluginSettingsHost`, and `SettingsDockWidgets` → `PluginHostService`); `plugin-api-impl.ts` → `tags/tag-vocabulary.service.ts` → `PluginHostService`. They work because Angular resolves services late, but load order inside a cycle is fragile. | (a) `DailyNoteService` opens documents, so it sits above `EditorService`: move it out of the `vault/` barrel. (b) Let `TagVocabularyService` and `SettingsDockWidgets` depend on a small interface or event instead of `PluginHostService` itself. |
| 4 | **The base's settings file holds plugin settings.** | `AppConfig` (`shared/config/schema.ts`, 802 lines; `normalize.ts`, 697) contains `actions`, `templates`, `entry` and the built-in prompt texts of the assistant and tags plugins. Four plugins read or patch the app config. A per-plugin config store exists beside it. | Adding a plugin setting can mean editing base files, which is the one place a feature still reaches into the core. Rule for new work: plugin settings go into the plugin's own config. Moving `actions` and the prompt texts to the assistant plugin is worth doing when that area is next touched — it changes the settings file, so it needs a decision ([ADR-0010](09_architecture_decisions/0010-app-settings-storage.md)). |
| 5 | **The plugin host names one plugin, and each cross-plugin need adds a base seam.** | `PluginHostDeps` carries `assistantToolbox` and `tagSuggester`; `electron/mcp-client/assistant-toolbox.ts` and `electron/llm/tag-suggest.ts` are feature logic inside the base; write requests carry `origin: 'assistant'`. Two provider slots (section search, task query; a third, semantic search, was removed in milestone 80) were each added by hand: an SDK member, a host field, a getter. The SDK is at minor version 21. | Not wrong — each seam was a considered decision — but the growth is linear in features. Before a third provider, consider one generic, typed service registry (`provide(key, service)` / `get(key)`) so that one plugin can offer data to another without a base change. A real alternative with trade-offs: it needs an ADR. |
| 6 | **The composition root is one long function.** | `electron/main.ts` is 1,135 lines; the `app.whenReady` callback runs about 365 of them and builds some twenty objects, several wired through lazy closures (`() => pluginHost?.…`) because of construction order. `plugin-host.ts` is 915 lines, of which `buildContext` is about 230. | Split `main.ts` into "build the services" (returns one typed object) and "window and lifecycle". Split `buildContext` by SDK namespace (`vault`, `llm`, `search`, …), one builder each. Behaviour-neutral, and each piece becomes testable on its own. |
| 7 | **`DailyNoteManager` writes into the vault on its own.** | `electron/daily-note.ts` creates the daily note and `templates/daily.md` with `fsp.writeFile`, not through `VaultManager`: the write is not entered in the own-write ledger. It also uses a fixed `templates` folder name, while the templates folder is a setting (`templates.dir`). | Route both writes through `VaultManager` and read the folder from the config. Worth checking as a possible defect: with another templates folder configured, the daily template is still looked for under `templates/`. |
| 8 | **Large modules that remain.** | `editor/markdown-surface/markdown-surface.ts` (1,038 lines, imports 31 modules), `electron/vault-manager.ts` (971: registry, file operations and the sidecar plumbing nothing needs any more), `dock/dock.service.ts` (904), `plugins/assistant/renderer/state.ts` (947), `app.ts` (imports 40 modules). | No urgency; split when next changed. `VaultManager` has the clearest cut: the vault registry apart from file operations, and the sidecar code deleted. |
| 9 | **This documentation is hard to read in two places.** | [§5](05_building_block_view.md) is about 3,600 lines, of which §5.1–§5.40 (some 2,700) are a milestone-by-milestone record, partly superseded. [§6](06_runtime_view.md) lists 57 flows in the order they were built, including replaced ones. | Done in this review: an overview at the top of §5, and sections 1, 3, 4, 8, 10 and 12 rewritten. Proposed, not done: move §5.1–§5.40 into an archive file and group §6 by topic. It changes section numbers that other documents link to, so it waits for the owner's word. |

What the review found in good order and would not change: the typed
bridge with one contract file per topic; plugins on two fixed channels
instead of one channel per feature; base panels registering through the
same call as plugin panels; vault file operations in one class (finding 7 is the exception);
pure logic in `shared/` rather than duplicated on both sides; the
earlier review's splits of `EditorService`, `FilesPanel` and the plugin
renderers, which held.

It costs about 55 MB of installed size. | Milestone 64 |
| `stdioBridgePath()` assumes electron-builder's `app.asar` layout | The packaged MCP stdio-bridge path is `app.getAppPath().replace(/app\.asar$/, 'app.asar.unpacked')` + the relative path. Correct for the current `asar: true` + `asarUnpack` setup; if asar is ever disabled the `$`-anchored replace is a harmless no-op (unpacked path == app dir), but a change to how electron-builder names the resources dir would need this revisited. | ADR-0023 |
| Renderer-only deps ride along in the packaged `node_modules` | `electron-builder`'s `files` can't know that `@angular/*`, `@codemirror/*`, `codemirror`, `markdown-it`, `rxjs`, `tslib` are already inlined into `dist/drey/browser/` by `ng build` — only `nspell` / `dictionary-*` / `yaml` are genuine main-process runtime deps. They are shipped (compressed in the asar) rather than maintained in a fragile deny-list. A few MB; slim later if it matters. | ADR-0023 |

## Environment gotchas worth remembering

| Gotcha | Notes |
|---|---|
| `ELECTRON_RUN_AS_NODE` can leak from the parent shell | Some parent processes (e.g. an Electron-based host application's integrated terminal) already have this env var set, sometimes to an empty string. Electron only checks whether the key *exists*, not its value, so this silently makes `electron .` run as plain Node instead of bootstrapping the app (`require('electron')` resolves to the npm package's path-string helper; `app.whenReady` is `undefined`). Worked around in `scripts/run-electron.js`, which explicitly deletes the key before spawning Electron — do the same in any other place that spawns Electron directly. The Playwright E2E fixture (`e2e/fixtures/drey.ts`) is one such place and deletes the key before `_electron.launch`; without it the whole suite fails with "Process failed to launch". |
| `npm`'s install-scripts allowlist blocks Electron's own binary download | `node_modules/electron`'s postinstall (which fetches the actual `electron.exe`) doesn't run under npm's newer script-allowlist gate. Worked around with an explicit `postinstall` script in the project's own `package.json` (`node node_modules/electron/install.js`, idempotent) — that one always runs, since the allowlist only gates *dependency* scripts, not the root project's own. |
| `app.getPath('userData')` is keyed only by app *name*, not by project path | Electron derives the userData folder (`%APPDATA%\<name>\` on Windows) purely from `package.json`'s `"name"` field. Any other Electron app on the same machine that happens to use the same name reads/writes the same folder — including `vault-manager.ts`'s `vault-config.json`. Confirmed harmless so far (this machine has no other app named `drey`), but worth remembering if that ever changes: rename via `package.json`'s `"name"` (and, once electron-builder is configured for packaging, its `appId`) to something more collision-resistant if this becomes a real concern. |
| A **stale main process** after a `shared/`, `electron/` or `plugins/` change — outside `npm run dev` | **Resolved for `npm run dev`** (2026-10-11): `scripts/dev-electron.mjs` watches the three folders, rebuilds the affected part of `dist-electron/` (main + preload, plugins, or both for `shared/`) and restarts Electron through an ordinary quit, so unsaved tabs ask first and the session is restored; a failed build restarts nothing. The trap itself remains wherever the app is built once: `npm run app`, the VS Code debug configs (`.vscode/`), a packed build. There `ng serve` or a rebuilt renderer can run against an older main process, and because `shared/` compiles into **both** contexts the two sides disagree about the IPC contract at runtime while the source typechecks. Observed failure, before the watcher: adding `llm.apiKey` — the renderer sent the field, the stale main process's `normalizeAppConfig` stripped it and returned the stripped config; the key vanished from the input as it was typed. Quick check: `grep <new-field> dist-electron/shared/*.js`. |
| VS Code tasks/debug launches don't inherit `env.ps1`'s PATH | Each task/debug session spawns its own shell that never sources `env.ps1`, so a naive `npm run ...` task or a `runtimeExecutable` pointing at `node_modules/.bin/electron(.cmd)` fails to find `node`/`npm` (that shim falls back to a bare `node` on PATH when no `node.exe` sits next to it). Worked around three ways, see `.vscode/`: `tasks.json` has a top-level `options.env.PATH` prepending `.tools/node`; the Electron debug configs in `launch.json` point `runtimeExecutable` straight at `.tools/node/node.exe` with `program` set to `node_modules/electron/cli.js` (no PATH dependency at all); `settings.json` gives the integrated terminal a default profile that sources `env.ps1` on open, for anything typed by hand. |
