# 11. Risks and Technical Debt

Carried over from `specs/roadmap.md` ("Open Risks / Undecided Details"),
tracked here so they stay visible as the app is built:

| Risk | Notes | Status |
|---|---|---|
| Autosave-vs-watcher conflict | Concrete UX not yet defined (diff view? conflict copy? undo?). Roadmap only commits to a minimum: surface as a warning with "keep mine / take external version". | Partially addressed by the watcher (ADR-0045): the watcher now exists (opt-in), and a **clean** open tab auto-reloads from disk. A **dirty** tab is deliberately untouched — last-writer-wins on save, silently. The keep-mine/take-external dialog remains unbuilt; revisit if it bites in practice. |
| Model contention | Classifier/embeddings vs. benchmarking models sharing LM Studio (RTX 4080, 12GB VRAM) — needs an availability check before every call. | Open — relevant from milestone 6 (LM Studio client) onward. |
| Folder sprawl from LLM suggestions | Inbox review acts as a brake, but no guarantee against near-duplicate tags (e.g. "sailing" vs. "boat"). | Open — relevant from milestone 7 (batch tag suggestion) onward. |
| Tag registry scaling | Prompt 2's registry is fine under ~50 tags; a much larger vault would need pre-filtering instead of the full list in-prompt. | Noted, not an MVP concern (`specs/classifier-spec.md`, "Scaling note"). |
| Structured-output enforcement | Small local models sometimes ignore "JSON only" prompt instructions. Should use LM Studio's `response_format` JSON-schema/grammar constraining if the chosen model supports it — unverified so far. | Open — needs a check before milestone 6 relies on unconstrained JSON parsing. |

## Technical debt

| Item | Notes | Since |
|---|---|---|
| Preload runs without the OS-level Electron sandbox (`sandbox: false`) | `contextIsolation: true` and `nodeIntegration: false` are still on (the two properties ADR-0001 commits to), but the extra process sandbox is off because a sandboxed preload's `require()` can't load `shared/ipc-api.js`. Fix: give preload its own bundling step (e.g. esbuild) that inlines `shared/` into one file with no runtime `require()`, then re-enable. | Milestone 1 |
| No feedback when the hotkey fires with no vault selected | `openTodayDailyNote` raises the window and logs a warning; the only user-visible cue is the sidebar's "no vault" state. A renderer toast would be better. | Milestone 4 |
| Hotkey vs. a dirty non-daily buffer | If another file is open with unsaved changes, the hotkey's `openFile` shows the milestone-3 `confirm()`; declining leaves you where you were with no daily note opened. Acceptable until the real conflict UX lands; note the file watcher (ADR-0045) arrived *without* that UX — dirty tabs stay last-writer-wins by design. | Milestone 4 |
| `TagIndex` is a full rescan, and stale on external edits | `TagIndex.rebuild()` reads and parses every `.md` in the vault; it runs on `vault:select` and after any `note:save` that changed the tag set. Cheap for a personal vault (dozens–hundreds of small files), wasteful for a large one. With no file watcher, a master doc edited outside the app (or in another editor tab) is not reflected until the next rebuild. Incremental update + watcher integration deferred. | Milestone 6a. Watcher integration has landed (ADR-0045): with the watcher on, external `.md` changes arrive as scoped `write` events that re-index just that file (`reindexFile`); with it off, or after the manual refresh (now a full round), the rescan is the mechanism. Full-rescan cost on those paths unchanged. |
| `TagIndex` / `NoteManager` have no unit-test harness | Vitest only runs `src/**/*.spec.ts` (`tsconfig.spec.json`), so `electron/` classes are untestable in place. All branching logic lives in pure `shared/` modules (`frontmatter.ts`, `inline-tags.ts`, `tag-registry.ts`, and 6b's `entries.ts` / `history.ts`), covered from `src` specs; the two classes only sequence fs calls. A real fix is a `vi.mock('electron')` harness or an integration test. | Milestone 6a |
| EOL restore moved into `NoteManager`, uncovered | The `\n` → file-EOL transform used to be in `EditorService` (unit-tested); it is now one line in `NoteManager.saveNote` (`eol === '\r\n' ? …`). The renderer test only asserts the `eol` flag is forwarded. | Milestone 6a |
| Root `<tag>.md` → `<tag>/_index.md` promotion not implemented | Routing only appends to a master document that already exists (whether at the vault root or as `<tag>/_index.md`). The first-topic-growth promotion — turning `<tag>.md` into `<tag>/_index.md` and sweeping loose sibling notes into the folder — is a real filesystem operation with edge cases, deferred past milestone 6. See [ADR-0006](09_architecture_decisions/0006-master-document-tag-mechanism.md). | Milestone 6 |
| History append is end-of-section, not date-sorted | `appendHistoryEntry` appends each routed entry after the last `## History` entry rather than inserting in chronological order. Fine when entries arrive roughly in order (the common case); an out-of-order save lands out of order. | Milestone 6b |
| A dirty open master tab is not reloaded after a routed append | `EditorService` reloads a master doc that gained a History entry only if its tab has no unsaved edits — a dirty one keeps the stale buffer and would overwrite the routed entry on its next save. Same underlying gap as autosave-vs-watcher; acceptable until the watcher's keep-mine/take-external UX exists. | Milestone 6b |
| Routing bumps every target master's `updated:` | Each `appendHistoryEntry` write also re-serialises the master's frontmatter to bump `updated:` (consistent with "updated bumps on every change"), so a save that routes into three masters rewrites three files. Cheap, but more disk churn / git noise than a body-only append. | Milestone 6b |
| `parseDatedEntries` heuristic | A line like `## 14:32 Standup` (time followed by a title with **no dash**) is still treated as prose, not an entry heading; a note that titles its entries that way would not route. Since Feature B the dashed form `## 14:32 — Standup` *is* an entry, so the drawer's own output routes — but hand-written headings still have to use the dash. | Milestone 6b, narrowed in Feature B |
| `on-save` Actions run LLM calls inside the `note:save` round-trip | An enabled `on-save` trigger makes a (possibly slow) `/chat/completions` call before `saveNote` returns, so a save can block for the model's latency. `'noop'`/`'error'` outcomes are swallowed so a save never fails, but there is no timeout-to-background or progress cue yet. No default `on-save` trigger ships, so this only bites if the user adds one. A job queue (Phase 4) is the real home for this. | Settings/Actions milestone |
| `ActionRunner`, `AppConfigStore`, `LmStudioClient`, `ClassifierService` have no unit-test harness | Same `electron/`-is-untestable gap as `TagIndex`/`NoteManager`. All logic is in pure `shared/` modules (`app-config.ts`, `classifier.ts`, `actions.ts`, `action-apply.ts`, `llm.ts`, `text-diff.ts`), covered from `src` specs; these classes only sequence fetch/fs/registry calls. The HTTP shapes in `LmStudioClient` (request body, `data[].id` / `choices[0].message.content` extraction) are covered by neither. | Settings/Actions milestone |
| The LLM API key is stored in plain text | `llm.apiKey` sits unencrypted in `app-config.json` under `userData`. Accepted for a **localhost** bearer token: anyone who can read that file already runs as this user and could call the endpoint directly. Electron's `safeStorage` was weighed and rejected (separate encrypted blob, config no longer hand-editable, `isEncryptionAvailable()` false on some Linux setups) — see [ADR-0010](09_architecture_decisions/0010-app-settings-storage.md). **Revisit if a remote/cloud provider key is ever stored here**, which is a different threat model. | Settings/Actions milestone |
| The LLM debug log holds note content in memory | Every request body is recorded (truncated to 2 kB), and a chat/action request body contains the document being worked on. Kept **in memory only**, capped at 50 entries, cleared on quit and by the pane's "Clear" — never written to disk, never leaves the machine. Bearer tokens are masked before an entry is created, so nothing in the panel (or a screenshot of it) carries the real key; "Copy curl (with key)" re-inserts it in the renderer as an explicit action. Worth re-checking if the log ever gains persistence or export. | Settings/Actions milestone |

The "anchored entry" gate was removed at the same time — it made the squiggles appear late enough to look broken. | Feature B, resolved on review |

## Environment gotchas worth remembering

| Gotcha | Notes |
|---|---|
| `ELECTRON_RUN_AS_NODE` can leak from the parent shell | Some parent processes (e.g. an Electron-based host application's integrated terminal) already have this env var set, sometimes to an empty string. Electron only checks whether the key *exists*, not its value, so this silently makes `electron .` run as plain Node instead of bootstrapping the app (`require('electron')` resolves to the npm package's path-string helper; `app.whenReady` is `undefined`). Worked around in `scripts/run-electron.js`, which explicitly deletes the key before spawning Electron — do the same in any other place that spawns Electron directly. The Playwright E2E fixture (`e2e/fixtures/drey.ts`) is one such place and deletes the key before `_electron.launch`; without it the whole suite fails with "Process failed to launch". |
| `npm`'s install-scripts allowlist blocks Electron's own binary download | `node_modules/electron`'s postinstall (which fetches the actual `electron.exe`) doesn't run under npm's newer script-allowlist gate. Worked around with an explicit `postinstall` script in the project's own `package.json` (`node node_modules/electron/install.js`, idempotent) — that one always runs, since the allowlist only gates *dependency* scripts, not the root project's own. |
| `app.getPath('userData')` is keyed only by app *name*, not by project path | Electron derives the userData folder (`%APPDATA%\<name>\` on Windows) purely from `package.json`'s `"name"` field. Any other Electron app on the same machine that happens to use the same name reads/writes the same folder — including `vault-manager.ts`'s `vault-config.json`. Confirmed harmless so far (this machine has no other app named `drey`), but worth remembering if that ever changes: rename via `package.json`'s `"name"` (and, once electron-builder is configured for packaging, its `appId`) to something more collision-resistant if this becomes a real concern. |
| `npm run dev` leaves a **stale main process** after any `shared/` or `electron/` change | `dev:electron` runs `npm run build:electron` exactly once, at startup. `ng serve` then hot-reloads the renderer on every save, but nothing rebuilds `dist-electron/` or restarts Electron. Because `shared/` compiles into **both** contexts, the two sides can disagree about the IPC contract at runtime while the source typechecks perfectly. Observed failure: adding `llm.apiKey` — the hot-reloaded renderer sent the field, the stale main process's `normalizeAppConfig` didn't know it, stripped it, and returned the stripped config, which the renderer then adopted; the key vanished from the input as you typed it and never reached disk. **After touching `shared/` or `electron/`, restart the dev session (or run `npm run build:electron` and restart Electron).** Quick check: `grep <new-field> dist-electron/shared/*.js`. A `tsc --watch` + auto-restart dev loop would remove the trap; not built yet. The Settings screen's draft/Save model (ADR-0010) means such a mismatch can no longer destroy in-progress input, only fail an explicit Save. |
| VS Code tasks/debug launches don't inherit `env.ps1`'s PATH | Each task/debug session spawns its own shell that never sources `env.ps1`, so a naive `npm run ...` task or a `runtimeExecutable` pointing at `node_modules/.bin/electron(.cmd)` fails to find `node`/`npm` (that shim falls back to a bare `node` on PATH when no `node.exe` sits next to it). Worked around three ways, see `.vscode/`: `tasks.json` has a top-level `options.env.PATH` prepending `.tools/node`; the Electron debug configs in `launch.json` point `runtimeExecutable` straight at `.tools/node/node.exe` with `program` set to `node_modules/electron/cli.js` (no PATH dependency at all); `settings.json` gives the integrated terminal a default profile that sources `env.ps1` on open, for anything typed by hand. |
